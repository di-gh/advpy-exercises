## 1. Задача

Есть тестовый стенд: Hadoop, Greenplum 5 и приложение, которое архивирует исторические данные из таблиц Greenplum в Hadoop. Нужно написать автотесты, начиная с приоритетных бизнес-функций.

## 2. Что известно о системе

### 2.1 Приложение

- Пользователи через веб-интерфейс задают период архивации либо выбирают архивацию таблицы целиком.
- У веб-приложения есть backend API.
- Backend с Airflow связан только через служебную БД: backend пишет задание в Postgres, Airflow его обрабатывает (предположение, нужно подтвердить: по расписанию или сенсором).
- Оркестрация сделана в Airflow 2.10.5, логика приложения «сращена» с оркестратором, поэтому вытащить её отдельно от Airflow неудобно.
- Выгрузка: внешняя таблица PXF, формат Parquet с кодеком gzip.
- Очистка источника в Greenplum: TRUNCATE партиций, если таблица партиционирована; если партиций нет, то DELETE по фильтру.
- Верификация перед удалением существует (детали не известны).
- Метаданные и логи приложения хранятся в отдельной БД Postgres.

### 2.2 Стенд и версии

| Компонент | Стенд | Прод |
| --- | --- | --- |
| Greenplum | 5.28.4 (основа PostgreSQL 8.3) | не уточнялось |
| PXF | 6.5.0 | 6.0.1 |
| Hadoop | 2.8.5, Kerberos включён | не уточнялось |
| Airflow | 2.10.5 | не уточнялось |

Стенд общий: другие приложения работают с Hadoop, GP и PXF, но наше приложение (Airflow-очередь, метаданные, DAG) никто, кроме команды, не трогает. Команда небольшая, договориться об остановке PXF/HDFS для негативных тестов можно, но остановка затрагивает соседние приложения.

## 3. Принятые решения по подходу

### 3.1 Точки входа для тестов (по убыванию основного использования)

1. **Backend API**: основной вход. Тест создаёт задание через API, затем ждёт обработки.
2. **Airflow REST API v1** (в 2.10.5 доступен): статус DAG run и тасков, логи. Ожидание только опросом статуса с таймаутом, без `sleep`. Таймаут должен учитывать интервал опроса Airflow.
3. **Прямая вставка записи в служебную БД**: только в нескольких тестах, чтобы проверить звено «Airflow обработал задание» отдельно от «API создало запись». Не привязывать к схеме БД массово.
4. **UI-тесты (Playwright/Selenium)**: 3–5 тестов на ключевые пути (задать период, задать «целиком», посмотреть статус). Бизнес-логику через UI не проверять.
5. По возможности запуск отдельных тасков DAG (`airflow tasks test` или clear/run) для негативных тестов верификации.

### 3.2 Проверка выгрузки

- Независимый ридер: читать Parquet из HDFS не через PXF, а отдельно (pyarrow), чтобы ошибки записи и чтения не компенсировали друг друга.
- Способ доступа к HDFS (Kerberos, Hadoop 2.8.5): предпочтительно `hdfs dfs -get` на edge-ноде по SSH с последующим чтением Parquet локально через pyarrow. Альтернатива: WebHDFS со SPNEGO (если включён), Python-клиент `hdfs` с Kerberos. Прямой доступ pyarrow через libhdfs не рекомендуется (нужны JVM и клиентские библиотеки Hadoop).
- Сверка GP ↔ Parquet: число строк, контрольные суммы по колонкам (например md5 по строке), построчное сравнение выборки, совпадение схемы и типов.
- Проверка файлов: путь, формат, кодек gzip, число файлов, размер, права, владелец.
- Особое внимание типам: numeric (точность, масштаб), timestamp/timestamptz (часовые пояса), date, bytea, text с юникодом и спецсимволами, NULL против пустой строки, boolean, массивы (если используются). Маппинг типов в PXF для Parquet нетривиален, именно там чаще всего живут баги.

### 3.3 Особенности Greenplum 5.28.4

- Основа PostgreSQL 8.3: старый SQL, нет GENERATED, MERGE, jsonb-операций и многого другого, к чему привыкли в новых версиях.
- Состояние партиций проверять через `pg_partitions` и `pg_partition_rule`.
- Покрыть типы таблиц: heap, AO, AOCO; range/list-партиции; разные distribution key.

### 3.4 Изоляция на общем стенде (облегчённая)

- Одна тестовая схема в GP и один тестовый каталог в HDFS; уникальный суффикс на каждый тест (можно гонять параллельно).
- Фикстура создаёт тестовую таблицу и после теста удаляет таблицу, каталог в HDFS и записи в метаданных. Очистка обязательна, так как место в HDFS и ресурсы GP общие.
- Жёсткие защитные роли и ночные окна не нужны. Маркер `destructive` остаётся как удобная группа тестов.
- Реальную остановку PXF/HDFS оставить для 1–2 согласованных тестов. В остальных случаях имитировать сбой:
  - снять права записи на тестовый каталог HDFS у технического пользователя;
  - поставить квоту на тестовый каталог;
  - указать в внешней таблице несуществующий путь или битый профиль;
  - повредить Parquet-файл между записью и верификацией.
- Нагрузочные и объёмные тесты согласовывать с соседями, размеры держать умеренными.
- После прогона проверять, что сервисы подняты, иначе следующий прогон упадёт по ложным причинам.
- Kerberos: технический пользователь с keytab, `kinit` перед прогоном или `k5start`; права пользователя на HDFS по возможности ограничить тестовым каталогом.

### 3.5 Риск разницы версий PXF

Стенд на PXF 6.5.0, прод на 6.0.1. Поведение записи Parquet, кодеков и маппинга типов может отличаться. Меры:

- сверить release notes PXF между 6.0.1 и 6.5.0 в части Parquet;
- записывать версии компонентов в отчёт каждого прогона;
- по возможности разово прогнать набор типов данных на PXF 6.0.1 (на другом стенде);
- не делать выводов о проде по результатам стенда без этой оговорки.

## 4. Стек и структура проекта (предложение)

Python + pytest (если команда не на Java), psycopg2 для GP и метаданных, requests для API, Allure для отчётов, запуск в CI.

```
tests/
  conftest.py            # фикстуры: соединения, суффикс, очистка
  clients/
    gp.py                # psycopg2, создание/удаление таблиц, pg_partitions
    hdfs.py              # SSH + hdfs dfs (или WebHDFS), чтение Parquet
    airflow.py           # REST API v1: DAG run, статусы тасков, логи
    backend_api.py       # создание задания, получение статуса
    meta_db.py           # запросы к метаданным и логам
  data/
    generators.py        # генераторы данных, наборы типов
  checks/
    compare.py           # сверка GP <-> Parquet
    gp_state.py          # что удалено/осталось, партиции
  scenarios/
    test_archive_partitioned.py
    test_archive_nonpartitioned.py
    test_archive_full_table.py
    test_types.py
    test_verification.py
    test_failures.py     # маркер destructive
    test_input_validation.py
  ui/                    # 3-5 тестов Playwright
```

Маркеры: `smoke`, `regression`, `destructive`, `slow`.

## 5. Процесс (общий план)

1. Разобраться в приложении (запуск, правила отбора исторических данных, формат в Hadoop, поведение после архивации, метаданные).
2. Приоритизировать функции по цене ошибки и частоте использования.
3. Определить уровни тестов: smoke, функциональные E2E, негативные и отказоустойчивость, нефункциональные (позже).
4. Построить каркас: клиенты, конфиги окружений, секреты вне репозитория, отчёты, CI.
5. Подготовить генераторы тестовых данных (не ручные дампы), отдельно наборы для граничных дат и для объёмов.
6. Сделать библиотеку проверок (счётчики, контрольные суммы, схема, файлы, состояние GP, метаданные).
7. Писать тесты итерациями: smoke и happy path по главной функции, затем граничные случаи и негатив, затем следующая функция.
8. Стабилизация: убрать флаки, регулярный прогон, трассировка на требования.

Приоритет бизнес-функций (по риску): корректность архивации (полнота и целостность) → безопасность удаления из GP → отбор по критерию (границы, партиции) → сбои и перезапуск → восстановление из архива (если есть) → статусы, журналирование, метаданные → права, параллельные запуски, производительность.

## 6. Приоритетные сценарии

1. Happy path, партиционированная таблица, период = целые партиции. Полная сверка GP ↔ Parquet, нужные партиции очищены, соседние на месте, статус и метаданные корректны.
2. Happy path, непартиционированная таблица (DELETE по фильтру), включая граничные даты (начало и конец периода, соседние строки не задеты).
3. Режим «таблица целиком».
4. Набор типов данных: одна широкая таблица со всеми типами и крайними значениями.
5. Верификация не пройдена ⇒ удаления нет, статус «ошибка».
6. Сбой записи в HDFS/PXF ⇒ в GP ничего не тронуто, статус «ошибка».
7. Повторный запуск того же периода (идемпотентность: дубли, перезапись или отказ).
8. Период без данных и период частично вне данных.
9. Невалидный ввод: период «с > по», несуществующая таблица, нет прав.
10. Параллельные задания на одну таблицу.

### Критичные случаи удаления

- Период точно совпадает с границами партиций: удаляются только нужные партиции.
- Период попадает в партицию частично: TRUNCATE целой партиции уничтожил бы данные вне периода. Нужно выяснить, как приложение это обрабатывает (отказ, DELETE, архивация всей партиции).
- Default-партиция, многоуровневое партиционирование, пустые партиции, период без данных.
- Негатив: при неудачной записи в HDFS ничего не удаляется.

### Тесты верификации (защитный механизм)

- Подмена или повреждение Parquet-файла между записью и верификацией (удалить, обрезать, подменить данные): удаление не выполняется, статус «ошибка».
- Расхождение числа строк при совпадающих контрольных суммах и наоборот (зависит от устройства проверки).
- Недоступность HDFS или PXF во время проверки.

### Проверки метаданных

Статусы заданий и переходы между ними, периоды и объёмы, сообщения об ошибках. Согласованность: «успешно» в метаданных ⇒ данные в HDFS есть, в GP удалены; при сбое статус не должен врать.

## 7. Открытые вопросы

Отмечены по приоритету для старта. Пункты 1–4 достаточно, чтобы написать каркас и первые два теста.

### Критично для старта

1. **Backend API**: пример запроса на создание задания и ответа (скопировать из вкладки Network), запрос статуса, способ аутентификации.
2. **Служебная БД Postgres**: DDL таблиц и пример строк (успешное и упавшее задание). Как задание переходит из «создано» в «взято в работу» и кто это делает.
3. **DAG**: `dag_id`, список тасков и порядок, расписание или сенсор, интервал опроса, как берутся задания (все сразу или по одному), пример `conf`. Достаточно описания или кода.
4. **Таблицы**: DDL 2–3 типичных таблиц (партиционированная и нет) и DDL соответствующих внешних таблиц PXF. Создаются ли внешние таблицы приложением каждый раз или существуют заранее.

### Важно для содержательных тестов

5. **Верификация**: что сравнивается (count, хэш, какие колонки), на каком шаге DAG выполняется.
6. **HDFS**: схема каталогов и пример пути архива; что происходит при повторной архивации того же периода.
7. **Частичное попадание периода в партицию**: как приложение это обрабатывает.
8. **Реестр или whitelist таблиц**: есть ли ограничение на архивируемые таблицы и как добавить тестовую.
9. **Восстановление из архива**: есть ли такая функция.
10. **Известные баги и инциденты**: подскажут, куда бить в первую очередь.

### Доступы и инфраструктура

11. Аутентификация в Airflow API (basic, session и т. д.); есть ли WebHDFS; SSH на edge-ноду; keytab технического пользователя.
12. Права на тестовую схему GP и тестовый каталог HDFS; возможность задать квоту и менять права для негативных тестов.
13. Версии Airflow, Hadoop и GP на проде; есть ли стенд с PXF 6.0.1.
14. Есть ли CI и какой (для запуска и отчётов).

### Команда и сроки

15. Стек команды: язык (Python или Java), репозиторий, инструмент отчётности.
16. Есть ли ручные тест-кейсы, чек-листы или тестовая документация (быстрый старт).
17. Сроки и ожидаемый объём покрытия первой итерации.
18. Бизнес-приоритеты функций (подтвердить или скорректировать порядок из раздела 6).
